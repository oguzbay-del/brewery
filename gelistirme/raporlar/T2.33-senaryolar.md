# T2.33 — End-to-end scenarios

These scenarios use the OpenAPI contract in `sozlesme/openapi/openapi.json`. They describe test cases. They do not implement test code.

## Scenario 1 — Home user completes the main flow

```gherkin
Feature: Home user workflow

  Scenario: Sign in, create a workspace, brew a batch and contact support
    Given the user has a valid Apple ID token
    When the client sends POST /v1/auth/nonce
    Then the response status is 201
    When the client sends POST /v1/auth/apple with the ID token and nonce
    Then the response status is 200
    When the client sends GET /v1/me/session
    Then the response status is 200
    When the client sends POST /v1/workspaces with mode "home"
    Then the response status is 201
    And the user is the first workspace member with the administrator role
    When the client sends POST /v1/workspaces/{workspace_id}/recipes
    Then the response status is 201
    And the response contains the recipe ID and the first draft version ID
    When the client sends POST /v1/workspaces/{workspace_id}/recipe-versions/{version_id}/publish
    Then the response status is 200
    And the response contains the published version
    When the client sends POST /v1/workspaces/{workspace_id}/batches
    Then the response status is 201
    And the batch starts in stage "planned"
    When the client sends POST /v1/workspaces/{workspace_id}/batches/{batch_id}/brew-day-package
    Then the response status is 201
    And the response contains the signed package and its package ID
    When the client sends POST /v1/workspaces/{workspace_id}/batches/{batch_id}/measurements
    Then the response status is 200
    And each measurement result is "created" or "duplicate"
    When the client sends GET /v1/workspaces/{workspace_id}/notifications
    Then the response status is 200
    When the client sends POST /v1/workspaces/{workspace_id}/support/requests
    Then the response status is 201
    And the response contains the support request and its first message
```

## Scenario 2 — Workspace data stays isolated

```gherkin
Feature: Workspace isolation

  Scenario: User A cannot read data from workspace B
    Given user A has a valid session and belongs to workspace A
    And user B owns workspace B
    And user A is not a member of workspace B
    When user A sends GET /v1/workspaces/{workspace_B}/recipes
    Then the response status is 404
    When user A sends GET /v1/workspaces/{workspace_B}/batches
    Then the response status is 404
    When user A sends GET /v1/workspaces/{workspace_B}/notifications
    Then the response status is 404
    When user A sends GET /v1/workspaces/{workspace_B}/support/requests
    Then the response status is 404
    And no data from workspace B is returned
```

## Scenario 5 — A stale version returns 412

```gherkin
Feature: Optimistic concurrency

  Scenario: A stale recipe version update is rejected
    Given the user has a draft recipe version with ETag "v2"
    And another request has changed the version to ETag "v3"
    When the client sends PATCH /v1/workspaces/{workspace_id}/recipe-versions/{version_id}
    And the client sends If-Match "v2"
    Then the response status is 412
    And the response includes the current version and conflicting fields
    And the stale update does not change the draft
```

## Scenario 6 — A measurement with an invalid package signature is rejected

```gherkin
Feature: Brew day package verification

  Scenario: The server rejects a measurement that refers to a package with an invalid signature
    Given the batch has a brew day package
    And the package signature does not pass HMAC-SHA256 verification
    When the client sends POST /v1/workspaces/{workspace_id}/batches/{batch_id}/measurements with that package ID
    Then the response status is 422
    And the measurement is not stored
```

## Scenario 7 — Missing package key blocks package operations


## Contract references

| Step | Endpoint | Success status | Negative status used |
|---|---|---:|---:|
| Sign-in nonce | `POST /v1/auth/nonce` | 201 | — |
| Apple sign-in | `POST /v1/auth/apple` | 200 | 401 |
| Read session | `GET /v1/me/session` | 200 | 401 |
| Create Home workspace | `POST /v1/workspaces` | 201 | 401, 403 |
| Create recipe draft | `POST /v1/workspaces/{workspace_id}/recipes` | 201 | 401, 403 |
| Publish recipe version | `POST /v1/workspaces/{workspace_id}/recipe-versions/{version_id}/publish` | 200 | 401, 403, 412 |
| Create batch | `POST /v1/workspaces/{workspace_id}/batches` | 201 | 401, 403 |
| Create brew day package | `POST /v1/workspaces/{workspace_id}/batches/{batch_id}/brew-day-package` | 201 | 401, 403, 503 |
| Send measurements | `POST /v1/workspaces/{workspace_id}/batches/{batch_id}/measurements` | 200 | 401, 403, 422, 503 |
| List notifications | `GET /v1/workspaces/{workspace_id}/notifications` | 200 | 401, 403 |
| Create support request | `POST /v1/workspaces/{workspace_id}/support/requests` | 201 | 401, 403 |

## Contract notes

- Protected endpoints declare cookie or bearer authentication. The contract lists 401 for an unauthenticated request.
- The listed workspace endpoints include 403 and 404 responses. Scenario 2 uses 404 for a workspace that the caller cannot access.
- The recipe-version PATCH operation requires `If-Match`. Its description states that a stale value returns 412 with the current version and `conflicting_fields`.
- The measurement operation lists 422 for validation failure. The invalid-signature scenario uses this contract response.
- `gelistirme/DURUM.md` states that package endpoints return 503 when the package key is not configured.
- The OpenAPI contract does not define a separate response code for each role or package-signature failure. These scenarios use the general 403 and 422 responses that the relevant operations declare.
