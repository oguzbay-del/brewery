## 2. Art direction

- [Linear](https://linear.app/): study its product-led hierarchy, short technical explanations, real product context, and focused progression from one capability to the next. Do not copy its logo, code, product visuals, dark palette or distinctive graphical assets.
- [Aesop](https://www.aesop.com/): study quiet editorial rhythm, typography, photographic composition, restraint and material detail. Do not copy its imagery, typography assets, branding, copy, or storefront structure.
- GRISTORA: premium, confident, editorial, technical and human. Keep Forest Green #0B2F26, Amber Gold #F4A261, Stone Beige #F7F6F3 and Slate Gray #475569. Keep approved logo geometry, Plus Jakarta Sans, Inter and restrained editorial serif treatment. Keep professional breweries primary and homebrewers secondary. No generic dark dashboard look, decorative glow, excessive motion or unnecessary redesign.
- Start with a homepage pilot after audit and shared foundations. Use one focal point per section, purposeful negative space, concise heading/copy pairs, clear primary/secondary CTA hierarchy, authentic brewery photography and actual product screenshots. Use Editorial Light across both editorial and technical content. Dark Forest Green is restricted to existing brand anchors (hero, header/footer where appropriate and a restrained closing CTA); do not introduce recurring dark technical panels or a separate dark theme. Technical depth comes from hierarchy, real screenshots and precise layout, not dark backgrounds. Preserve existing useful stories, routes, SEO and translated meaning. Do not invent commercial outcomes or functionality. References are inspiration, not templates or permission to reuse assets.

## 3. Marketing foundations

Inventory existing Astro components, global and Stitch CSS, page classes, tokens, image utilities, tests and route templates before adding code. Extend existing CSS custom properties rather than introduce another token source. Preserve approved radii (10–12, 18, 24, pill) and colors. Keep gallery as a separate development build or dev-only fixture, absent from production dist, sitemap and navigation. No Storybook, React Aria or product UI Kit imports.

## 6. Marketing Visual Quality Gate

Use existing commands documented in README: npm run check, npm run build, npm run validate:site, npm run test:browser and current Lighthouse CI. Validate 320, 390, 768, 1024, 1440 CSS px and 200% zoom. Include EN/TR on representative routes and all changed page families. Keep mobile navigation, keyboard/focus, screen-reader manual checks and reduced motion. The iPad-only product support matrix does not apply to marketing.

Add targeted geometry checks for page overflow, nonintentional overlap, clipped meaningful text/controls, image ratios, CTA visibility and grid alignment. Exclude documented intended overlays, decorative layers and labelled scroll containers. Use deterministic screenshots (fixed browser, fonts, data, viewport and reduced motion). First report mode, then enforce only stable assertions. Baselines are protected; no automatic update or weakened thresholds. Visual evidence includes current SHA, preview URL, viewport, language and artifact location. Use native Playwright, axe WCAG 2.2 AA tags, current Lighthouse reports. Target LCP <=2.5s, INP <=200ms and CLS <=0.1 at field p75 when field data exists; lab Lighthouse is not field INP. No tracking or new paid service. CI results and preview review are separate from production readiness.

### 6.1 Repeatable visual test flow (owner decision 27 November 2026)

The visual quality gate must test appearance as well as functional browser behavior. Start MQ-11a now, independently of the UI Kit, to capture the existing site's evidence before redesign. Reuse the existing marketing browser tests and GitHub Actions; no extra paid service or dependency. Do not change protected workflow files without Claude approval.

1. **Build and smoke checks:** run existing check, build, static route/link/metadata validation and browser suite; keep all current hard assertions. Use a preview built from the exact head SHA. Record branch, head, run and preview URL; never substitute an old successful run.
2. **Route/state matrix:** cover EN/TR homepage, breweries, homebrewers, feature and module index plus one representative detail each, how-it-works, technical, FAQ, pricing, compare, configurator and 404. Include every changed route and both languages, add all routes to final release review. Capture the navigation closed/open, comparison scroll region, FAQ open/closed, configurator steps and validation/feedback where present. Test 320, 390, 768, 1024 and 1440 CSS px. Initially sample interactive states at 390/1440; expand based on defects. Cover long translated labels, real 200% browser zoom (manual if not reliably automated), prefers-reduced-motion, prefers-contrast more and forced-colors where supported. No dark mode test target for marketing.
3. **Deterministic screenshots:** use the existing Playwright browser/version and fixed viewport/height, device scale, language, font readiness, image decode, reduced motion and stable fixture data. Capture full page plus targeted viewport/section states. Keep filenames keyed by route, locale, width and state; record head SHA in manifest. No live screenshots altered or invented; no masking meaningful text or UI. Test responsive image crops visually.
4. **Geometry and accessibility:** measure document/body scroll width with 1 CSS px rounding allowance; check selected meaningful controls, headings, images and card layouts for off-viewport content, clipped text, unintended intersection and inconsistent alignment. Scope checks to comparable layout groups; exclude named intentional overlaps (hero overlays, open menus, sticky headers, labelled scrollable tables/diagrams, decorative layers) only with written rationale. Check image loading and intrinsic aspect ratio, visible CTA/focus, heading order, keyboard access, accessible names and axe WCAG 2.2 AA. Test text/background pairs (4.5:1 normal, 3:1 large text), meaningful control boundaries and graphics (3:1); verify hover/focus and text over photographs separately. Use browser-computed styles and alpha composition, not just hex pairs. Preserve native system colors under forced-colors. Do not use overflow:hidden or test exclusions to hide defects.
5. **Visual regression and human review:** capture an approved reference from a fixed commit and same rendering environment; compare candidate images and generate diff evidence using existing Playwright screenshot support. Begin in report mode: review every meaningful diff, not just the overall pixel count. Do not treat a changed pixel as automatically defective or a small diff as automatically safe. Baselines are protected; only approved CI baseline jobs and Claude review may create/commit them, no automatic updates. If no approved baseline exists, capture before/after evidence and report the gap, not a pass. Human review covers focal point, typography, spacing, hierarchy, composition, image readability/crop and EN/TR parity; automation cannot certify aesthetic quality.
6. **Defect report:** attach screenshot and report artifacts through existing CI output paths, with JSON/Markdown entries: defect key, URL, locale, viewport, browser, state, selector, expected, actual, severity, screenshot/diff reference and SHA. Deduplicate by root cause. P0 = content/action inaccessible or major broken layout; P1 = reproducible overlap, clipping, meaningful contrast or navigation/CTA failure, or major brand regression; P2 = local spacing/alignment/crop inconsistency; P3 = minor cosmetic issue. Record coverage gaps separately from actual observed defects. Fix the root cause in shared components/tokens, rerun the same scenario and related routes, then full marketing CI. Track unresolved P2/P3 in issues; no P0/P1 left open before visual acceptance. Do not certify screenshot review if files cannot be inspected.
7. **Merge and release:** compare only exact current head evidence, required CI green, no conflict or stop/fix label. Once stable geometry rules are proven, enforce them in CI rather than leaving permanent report-only tests; report-only success does not certify no visual defects. Keep protected baseline/workflow review requirements. Owner visual approval of homepage pilot before sitewide rollout; production approval remains separate. Existing checks may not be weakened.

At each marketing work run read DESIGN.md and this plan, use live area:marketing issues and PRs, continue current unfinished packages, run/check applicable gates and save checkpoints in GitHub. A marketing-only continuation does not modify product files. Use existing event/hourly loop if configured; do not claim unattended execution unless the task actually ran.

## 7. Designer Review Gate

Review each changed page against the approved direction with evidence, not a self-assigned score. Proposed rubric: brand 15, hierarchy 15, typography 10, grid/alignment 10, photography 10, product presentation 10, responsive 10, story 10, interaction/accessibility 10. Rate each 0–5, weighted sum out of 100; target 90 after a real review. Any critical accessibility, claims or layout error blocks acceptance independently of score. Record reviewer, date, commit, before/after screenshots, and required changes. Owner approval of homepage pilot is needed before broad rollout. Existing automated checks remain required.
