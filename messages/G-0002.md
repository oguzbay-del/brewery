## #217 — full export (no migration)
Verified schema:
- `water_profiles` is in the recipe/domain model and has a reference to `scanned_documents` via `source_document_id`.
- `devices` has `ingest_key_hash`; migration 0200 exposes only a narrow lookup function. Do not serialize the table row wholesale.
- `support_requests` and `support_messages` are in migration 0012. Messages have `visibility = customer | internal`; customer messages require `author_user_id`, staff messages can refer to `staff_users`.
- `attachments` (photo/note/file) and `scanned_documents` store `object_key`, `content_type`, `size_bytes`, `sha256`. `scanned_documents` has `legal_hold` and `retention_until`; export must not mutate retention or legal-hold state.
- `ObjectStore::get(key, max_bytes)` returns bounded bytes. It is appropriate for actual file bytes, but every read and cumulative ZIP content must remain under 512 MiB.
- Current `export.rs` checks the 512 MiB limit only while accumulating measurement CSV text. It does not yet account for the other JSON entries, ZIP entries or binary files. The final ZIP size must also be checked before storing.
- Existing manifest currently lists the five missing categories as `not_included_yet`.

Suggested tests:
1. One water profile, one device, one support request, one customer-visible message, one document and one photo; assert JSON entries and file bytes.
2. Device JSON excludes `ingest_key_hash` and every token/secret field; JSON contains no object-store keys.
3. Customer export excludes staff-only/internal support content unless an explicit product rule says otherwise.
4. Missing object, object larger than remaining budget, aggregate payload over 512 MiB, and exact-boundary size; each failure is recorded with a stable, clear error code and no completed object key.
5. Legal-hold/retention metadata is exported as metadata only; the source document is neither deleted nor altered.
6. ZIP entry names are deterministic and path-safe; duplicate attachment names do not overwrite each other.

Open product question: should `visibility = internal` support messages and staff-only diagnostics be excluded from the customer's workspace export? I recommend excluding internal messages and staff-only data.

## #212 — account deletion
Verified constraints:
- `users` has personal fields `display_name`, `contact_email`, `contact_email_verified_at`, `locale`, plus `deleted_at`; preserve its ID.
- `user_identities`, `passkeys`, `sessions` and `push_targets` are account-linked and contain provider subjects, refresh-token ciphertext, credential IDs/public keys, session hashes, push tokens and device metadata. These should be revoked/deleted or neutralized in a way consistent with foreign keys and audit requirements; never copy their secrets into audit values.
- The audit chain is append-only. Personal values must use the existing `changed_field()` anonymization rule; do not UPDATE/DELETE audit rows or change `canonical_row`.
- Existing `0191` is workspace-scoped soft-delete maintenance, not a suitable direct implementation of account deletion. Follow its RLS/grant conventions, but account deletion must use user-scoped policies and a worker-only due-job query.
- Owner decisions are final: grace setting default 30 days; GitHub support issue content is replaced and the issue closed, not deleted.

Suggested tests:
1. Request creates one pending row with scheduled purge using configured grace days; duplicate request behavior is deterministic.
2. Cancel only affects the caller's own pending request and records `restored_at`; cannot cancel another user's request or a done request.
3. Worker lists only due pending requests and safely handles retries/idempotency.
4. Anonymization preserves user ID and non-personal referential integrity; clears/revokes identity/session/passkey/push secrets per schema; repeated call is safe.
5. Audit chain verifies before and after anonymization; no PII is introduced into audit payloads.
6. RLS: app_api cannot read another user's request; app_worker can read/update due requests but cannot use unrestricted table access.
7. A user with immutable/ledger references does not cause a partial anonymization transaction.
