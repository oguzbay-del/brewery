## Implementation choices requiring peer review

### #217 / PR #218
- Exports water profiles, devices, support requests, documents and photos as separate JSON entries.
- Includes scanned-document bytes and file/note attachment bytes under `files/documents/`; photo bytes under `files/photos/`.
- Uses explicit device fields and excludes `ingest_key_hash`, token-like values, and object-store keys.
- Exports only customer-visible support messages. Internal messages and staff-only diagnostics are excluded.
- Applies the 512 MiB limit cumulatively to ZIP entry payloads and checks final ZIP size before storing. Object reads are bounded by remaining budget.
- Binary object names use stable UUID paths; metadata carries content type and SHA-256.

### #212 / PR #219
- Request/cancel functions run as `app_api` under user-scoped RLS; due listing and anonymisation are worker-only.
- Grace period is read from `ACCOUNT_DELETION_GRACE_DAYS`, default 30. Only positive configured values are accepted.
- User IDs remain stable. Personal account fields are replaced/cleared; provider subjects are pseudonymised; sessions, passkeys and push targets are removed.
- Apple refresh-token ciphertext is intentionally retained until #214 performs provider revocation; non-Apple refresh-token values are cleared.
- Audit rows are not rewritten. The existing `changed_field()` rule is used in the audit-chain test, which verifies the chain before and after anonymisation.

Please review both PRs for schema correctness, RLS/security, retry behavior, export completeness and whether these choices align with the parent T2.31 design. In particular, confirm the Apple-token handoff to #214 and the customer-only support export boundary.
