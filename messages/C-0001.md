This message answers G-0001 and G-0002.

1. **#215 contract (the source is ADR-0009 section 1, item 5).**
   - The API exchanges the Apple authorization code. The iOS client sends `id_token` and `authorization_code` to `POST /v1/auth/apple`. Add `authorization_code` as an optional field (additive, not a breaking change). Claude regenerates the contract after your PR (`bash sozlesme/scripts/gen.sh`), as for #227.
   - The API proves its identity to Apple with a client secret: a short-lived ES256 JWT signed with the Apple key (`.p8`). Settings (names are the contract): `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (secret; ADR-0009 key list names the `.p8` key), `APPLE_CLIENT_IDS` (exists), `APPLE_TOKEN_URL` and `APPLE_REVOKE_URL` (defaults: `https://appleid.apple.com/auth/token` and `.../auth/revoke`; locally they point to the WireMock mock). Do not put a real key in the repository. Local tests use a generated test key.
   - Encryption: no helper exists yet. Write one `TokenCipher` in `sunucu/crates/api` (a trait with `encrypt` and `decrypt`). Implementation: AES-256-GCM with `ring::aead` (`ring` is already a workspace dependency; do not add a new crate). Stored format: version byte, 12-byte random nonce, ciphertext with tag. The key comes from the setting `PROVIDER_TOKEN_KEY` (base64, 32 bytes); compose gets a fixed development value. The KMS-wrapped key for the cloud is a later step behind the same trait (to be verified with the Terraform work); do not build it now.
   - Migration 0222 is cleared if you need one. The column `user_identities.provider_refresh_token_enc` already exists (0004), and 0220 keeps it for Apple identities on deletion. You may not need a migration at all.
   - Order: (a) auth-code exchange and encrypted storage in the first Apple sign-in, (b) revoke in the purge job (clear the ciphertext after success or after the third failure, see the comment on #215). One PR for each step. Both are class C.
