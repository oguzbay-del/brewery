Thank you. Your analysis is correct. Add a new migration for #214: `sunucu/migrations/0221_hesap_silme_isci.sql`. Do not change 0220.

## Common rules for all new functions

- Make each function `SECURITY DEFINER` with `SET search_path = pg_catalog, public, pg_temp`.
- `REVOKE ALL ... FROM PUBLIC`. `GRANT EXECUTE` to `app_worker` only.
- Each function that takes `p_user_id` must refuse a user without a due `pending` request. Use the same guard as `anonymize_user` (lock the request row `FOR UPDATE`).
- Do not add direct table grants to `app_worker`.

## 1. Memberships

`account_deletion_memberships(p_user_id uuid)` returns `(workspace_id uuid, mode text, member_status text, other_active_members integer)`. Include `active` and `disabled` rows where `deleted_at IS NULL`.

## 2. Home workspaces

A Home workspace of the user is a `mode = 'home'` workspace where the user is the only member.

- `account_deletion_soft_delete_home(p_user_id uuid)` sets `deleted_at = now()` on these workspaces and returns their IDs.
- Then the job calls the existing `purge_workspace` immediately. The 30-day wait of `purge_workspace` does not apply here. Reason: the account request already had its grace period.
- A retention rule (legal hold) can stop the purge. Then log the workspace ID in `maintenance_runs` and keep the request `pending`. The next run tries again.

## 3. Business workspaces

`account_deletion_leave_business(p_user_id uuid)` sets `status = 'disabled'` and `deleted_at = now()` on the Business memberships of the user.

- Do not delete business records. `created_by` and `updated_by` keep the user ID; `anonymize_user` removes the personal data.
- If the user is the last active member with the owner role, do not remove the membership. Raise an exception with a clear code (`last_owner`). The job logs it and keeps the request `pending`. Support must transfer the owner role. Find the role model in `0005_uyelik_ve_yetki.sql`.

## 4. Object keys

`account_deletion_object_keys(p_workspace_id uuid)` returns the `object_key` values of all file tables for one soft-deleted Home workspace. Read the tables with an `object_key` column (example: `0011_bildirim_cihaz_dosya.sql`). Refuse a workspace that is not soft-deleted.

Use this order in the job:

1. Read the keys.
2. Run `purge_workspace` and commit.
3. Delete the objects with the `storage` crate.

If an object delete fails, write the remaining keys into the details of the `maintenance_runs` row. The next run deletes them. Do not delete objects before the database purge commits. Reason: a failed purge must not lose files.

## 5. Support `deletion_request`

The worker already applies `support_corrections` (0184). Add `account_deletion_from_support(p_correction_id uuid)`.

- It reads the correction of kind `deletion_request`. The user is `params->>'user_id'`. That user must be a member of the workspace of the correction.
- It creates a `pending` request with the standard grace period, through the same insert as `request_account_deletion`. If a pending request exists, it returns that request.
- It marks the correction as applied, in the same way as the other correction kinds.
- This function has no due-request guard. It creates the request.

## 6. Order in the hourly job

For each row of `due_account_deletions`:

1. `account_deletion_leave_business`
2. `account_deletion_soft_delete_home`
3. Read the object keys, then `purge_workspace`
4. `anonymize_user` (it sets `done`)
5. Delete the objects.

Use one transaction for steps 1 to 4 for each user. If a step fails, roll back that user only and continue with the next user. Write one `maintenance_runs` row for each run.
